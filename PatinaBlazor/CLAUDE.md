# PatinaBlazor Project Notes

## Project Purpose & Context

### What PatinaBlazor Is
A personal web app with modular, independent features. The name "Patina" reflects the core concept — aged, valuable antique items. Features are designed to be self-contained so each area of the app can grow independently without coupling.

### Features
- **Collections / Collectables** — The original and core feature. Allows tracking of antique collections. Still being refined.
- **Chat (IRC Bridge)** — A mIRC-style chat interface that bridges to IRC networks. A Python IRC bot logs events to the app via REST API; admins can monitor live IRC activity in a retro terminal-style UI.
- **RV & Boat Storage** — Phase 1 (admin-only) of a storage rental business module: properties with photos, units with dimensions/pricing, and a Storage Admin dashboard with occupancy/revenue charts. See Working Checkpoint below. Customer self-signup and recurring billing are a planned Phase 2, not yet built.
- **Articles** — a content feature authored by "Article Publisher" or Admin users, with Markdown bodies, per-article audience gating (Public/RegisteredUsers/StorageCustomers), and optional featuring on the Home page. See Working Checkpoint below.
- *(Additional features are expected to be added over time in a modular way)*

### Design Philosophy
- Features should be modular and independent where it makes sense
- Primarily personal use, but potentially shared with others
- Prefer building on existing patterns in the codebase rather than introducing new ones

### External Documentation

Describes how bots connect to the SignalR hub, register channels, log events, and receive commands. **Keep this file up to date whenever the hub API changes** (new hub methods, changes to `IrcEventRequest`, new `ChatAction` values, or changes to the `ReceiveCommand` contract).

### Reusable Components — check here before hand-rolling markup

**`Components/ResponsiveImage.razor`** — the app's one component for displaying an `ImageAttachment` (added 2026-09-07). Blazor doesn't have ASP.NET Core's Razor Pages/MVC "tag helper" concept, so this is the idiomatic equivalent: a component you drop into markup like any other MudBlazor tag. **Use this instead of writing a raw `<img>` for any `ImageAttachment`-backed image** — it generates the `srcset`/`sizes` pair from `EffectiveThumbnailWidth`/`EffectiveMediumWidth` correctly every time, which was previously hand-copied (with real width bugs, see the 2026-09-06 `srcset` sizing fix above) into 5+ separate files.

```razor
<ResponsiveImage Image="article.GetMainImage()" Alt="@article.Title" Height="160px" />
```

Parameters:
- `Image` (`ImageAttachment?`, required) — typically `entity.GetMainImage()`. Null renders `Placeholder` (or a generic image icon) instead of an `<img>`.
- `Alt` — alt text.
- `Height` (default `"200px"`) — CSS height of the box.
- `FixedHeight` (default `true`) — `true`: the box is always exactly `Height` tall, cropping/filling to match (uniform grid tiles — card grids). `false`: the box only caps at `Height` and shrinks to the image's own rendered height otherwise (a single non-tiled image — an article's hero image, where a short landscape photo shouldn't leave a tall empty box).
- `Fit` (`ResponsiveImage.ObjectFit.Cover` default, or `.Contain`) — Cover crops to fill (grid tiles, where showing the whole image isn't essential). Contain shrinks to fit entirely inside the box, letterboxed (anywhere cropping would hide real content — an article hero, a collectable's detail photo). **Getting this wrong is exactly the bug that prompted building this component**: the old hand-rolled `ArticleDetails.razor` hero image used Cover with a fixed height, which cropped a very different percentage of a portrait photo depending on viewport width (mobile showed most of the photo, desktop showed a tight, zoomed-in crop of it) — see the 2026-09-07 "article hero-image cropping" fix above for the full diagnosis.
- `Sizes` (default `"(max-width: 600px) 100vw, (max-width: 960px) 50vw, 33vw"`, matching this app's 3-cards-per-row desktop grid) — override for a different layout, e.g. a full-width hero: `"(max-width: 960px) 100vw, 960px"`.
- `Class` / `BorderRadius` — passed through to the wrapper.
- `Placeholder` (`RenderFragment?`) — rendered instead of the generic image icon when `Image` is null, e.g. `<Placeholder><MudIcon Icon="@Icons.Material.Filled.Warehouse" .../></Placeholder>` for a more specific empty-state icon per entity type.
- `OnClick` (`EventCallback`) — adds `cursor: pointer` and invokes the callback on click; used for click-to-zoom into `ImageModal`. Wrap in a `<div style="position: relative;">` alongside an absolutely-positioned overlay (e.g. a remove button) exactly like `ArticleDialog.razor`'s existing-images grid does — the component itself doesn't manage overlays, it's just the image box.

**Deliberately out of scope** (still hand-rolled `<img>`, and should stay that way): `ImageModal.razor`'s own full-size lightbox display (wants the single largest image, not a responsive srcset choice); `AppShell.razor`'s static logo (not an `ImageAttachment` at all); `AddCollectable.razor`/`EditCollectable.razor`'s "newly selected, not yet uploaded" file preview grids (JS-generated blob URLs, no `ImageAttachment` exists yet to hand the component); `CollectionDetails.razor`'s 60×60 avatar-style thumbnail in the "Add Collectable" picker list (too small to benefit from responsive sizing, and the component's flex-centered wrapper doesn't currently support an explicit pixel width the way that spot wants — would need a `Width` parameter added first if a similar tiny-avatar spot comes up again).

**If you add a new place that displays an `ImageAttachment`-backed image, use `ResponsiveImage` — don't hand-write another `<img src srcset sizes>` block.** If it can't cover a genuinely new case, extend the component's parameters (and update this doc) rather than reintroducing a duplicate, un-DRY block elsewhere.

- **Important constraint discovered during the migration**: `MudTextField`/`MudCheckBox`/other Mud form inputs do NOT render an HTML `name` attribute, so they cannot bind through Blazor's static-SSR `EditForm method="post"` + `[SupplyParameterFromForm]` model. All of ASP.NET Core Identity's scaffolded `/Account` pages render as static SSR (required for cookie-setting POST forms) — so those pages keep the native `InputText`/`InputCheckbox`/etc. (with their original Bootstrap-era CSS classes) for every actually-bound form field, and only use MudBlazor components for layout/buttons/alerts/headings around them. Same reasoning applies to a handful of native `<button name=... value=...>`/`<button form="...">` elements elsewhere in the Account area (external-login provider selection, `Email.razor`'s send-verification button) — deliberately left un-migrated since they rely on raw form attributes MudButton doesn't replicate. If a future page needs form-bound inputs under static SSR, don't reach for Mud input components there.
- **Post-migration bug fixed (2026-08-30)**: after the MudBlazor migration, the app loaded but the hamburger menu/drawer was completely unresponsive. Root cause: `MudPopoverProvider` (inside `Components/Layout/MudProviders.razor`) threw `InvalidOperationException: Duplicate MudPopoverProvider detected` on every page load, which crashed the entire Blazor Server circuit immediately after connecting (visible in browser console as "unhandled exception on the current circuit" + silent disconnect) — killing ALL interactivity on the page, not just the menu, since the whole circuit died. Root topology cause: `MainLayout.razor` renders multiple independent `@rendermode="InteractiveServer"` islands side by side (`MudProviders`, `AppShell`, and `@Body`'s own per-page render mode) — a valid but non-default arrangement that trips MudBlazor's duplicate-provider guard as a false positive even though `MudPopoverProvider` is declared exactly once. Fixed in `Program.cs` by configuring `AddMudServices(config => config.PopoverOptions.ThrowOnDuplicateProvider = false)` — this is MudBlazor's own documented escape hatch for this exact check (named directly in its error message). Also fixed in the same pass: `AppMudTheme.cs`'s `PaletteDark` had no `Secondary` color set, so every `MudText`/`MudButton` etc. using `Color="Color.Secondary"` (used throughout for muted text) rendered in MudBlazor's stock pink/magenta default instead of the intended muted gray — fixed by setting `Secondary = "#8b949e"` to match `TextSecondary`. If new MudBlazor circuit-crash or stray-default-color symptoms show up after further UI changes, check these two spots first.
- **Post-migration bug fixed (2026-08-30)**: the drawer, when opened, was partially covered by the app bar at the top instead of sliding out fully below it. Root cause, confirmed via computed styles in the browser: MudBlazor's default z-index is `Drawer=1100` vs `AppBar=1300` (both `position:fixed`), AND separately the `mud-drawer-clipped-always` CSS rule that's supposed to offset the drawer's `top` to `var(--mud-appbar-height)` wasn't matching in this app's DOM structure — the drawer's computed `top` was `0px` even though `--mud-appbar-height: 64px` was correctly set at the layout root, so the drawer extended full-height from the very top of the viewport, behind the app bar. Fixed with an explicit override in `wwwroot/app.css`: `.mud-drawer.mud-drawer-clipped-always { top: var(--mud-appbar-height) !important; height: calc(100% - var(--mud-appbar-height)) !important; }`. This is a plain CSS file — changes here take effect on a browser refresh, no rebuild needed. `AppShell.razor` uses `ClipMode="DrawerClipMode.Always"` on the `MudDrawer`; if that's ever changed, re-verify this override still matches.
- **Post-migration bug fixed (2026-08-30)**: on short-content pages (e.g. a simplified `Home.razor`), the drawer/nav sidebar and dark background only extended as far as the page content instead of reaching the bottom of the viewport. Root cause: MudBlazor's `.mud-layout { height: 100% }` only resolves to a real pixel value if its ancestor chain (`body` → `html`) has a *definite* height — `app.css`'s `html, body` rule never set one, so the chain collapsed to content-height (`auto`) instead of the viewport. Fixed by adding `height: 100%;` to the existing `html, body` rule in `wwwroot/app.css`. Verified via `getBoundingClientRect()` in the browser: drawer/layout/body/html heights all now match `window.innerHeight` exactly regardless of content length, on both interactive (MudLayout) and static-SSR (Identity/AccountLayout) pages. Static CSS file — takes effect on refresh, no rebuild needed.
- **Sticky page-footer pattern established (2026-08-30)**: to let a page pin something (e.g. `HitCounter`) to the bottom of the viewport regardless of content length, `wwwroot/app.css` makes `.mud-main-content` a flex column with `min-height: calc(100vh - var(--mud-appbar-height))`, and `.mud-main-content > .content` (the `<article class="content">@Body</article>` wrapper in `MainLayout.razor`) a flex column filling it via `flex: 1 1 auto`. A page opts in by rendering a `<footer class="page-footer">...</footer>` as a **sibling** of its main content (not nested inside it) — `.page-footer`'s `margin-top: auto` then pushes it to the bottom of the available space. See `Components/Pages/Home.razor` for the reference usage (`<MudContainer>...</MudContainer>` followed by `<footer class="page-footer"><HitCounter PagePath="/" /></footer>` as two separate root-level elements). No Blazor plumbing (no `SectionOutlet`/cascading service) was needed since this is pure CSS — reuse the same `<footer class="page-footer">` sibling pattern on any other page that wants a sticky footer.

- **Two real image-upload bugs found and fixed (2026-09-05), reported by the user as a generic Blazor circuit error** (`Uncaught Error: There was an exception invoking 'NotifyChange'...`) when uploading new photos to an existing collectable in production:
  1. **Pre-existing bug, unrelated to any recent work**: `AddCollectable.razor`/`EditCollectable.razor`'s client-side image preview passed the C# `IBrowserFile` object itself through `JSRuntime.InvokeAsync("createObjectURL", file)` - in Blazor **Server**, this only marshals the file's metadata as JSON, never a real browser `File`/`Blob`, so `URL.createObjectURL()` always threw `TypeError: Overload resolution failed`. Fixed by giving both pages' `<InputFile>` a `@ref`, reading its `.Element` (an `ElementReference?` - confirmed via reflection that `InputFile` exposes this), and passing *that* plus an index to a new JS helper (`createObjectURLFromInput`) that reads the real file straight off the native `<input>`'s own `.files[index]`. This meant **every real browser-driven image upload was broken** from the moment the responsive-sizing pipeline was introduced, across Collectables and Storage alike - it only went unnoticed because every verification pass in this session used a fake `IBrowserFile` backed by a real `File.OpenRead()` `FileStream` (which supports sync reads fine), never Blazor's actual constrained stream. Fixed by buffering the stream into a `MemoryStream` via `CopyToAsync` (async-safe) first, then handing SkiaSharp the in-memory copy (sync-read-safe, since it's not doing real I/O). The legacy-image migration path (`SaveImageFromDiskAsync`, backed by a plain `File.OpenRead`) was never affected by this specific bug, which is why it verified fine earlier.

- **Orphaned-photo cleanup made uniform via `ISupportImageAttachments`, using an EF Core `SaveChanges` interceptor (2026-09-08)**: the previous entry's "noticed in passing" bug (`ArticleService.DeleteAsync` never cleaned up its photo files) turned out to also affect `StorageService.DeletePropertyAsync` - both were plain `Remove()` + `SaveChanges()`, never touching `IImageService` at all. Rather than patch each one by hand (the same class of gap that would keep recurring at every future call site), the fix is structural: new `Services/ImageCleanupSaveChangesInterceptor.cs` (an EF Core `SaveChangesInterceptor`, registered on `ApplicationDbContext`'s `DbContextOptions`) inspects every `SaveChanges`/`SaveChangesAsync` call for any tracked entity in `EntityState.Deleted` that implements `ISupportImageAttachments`, and deletes that entity's physical image files - regardless of which service or page triggered the delete. Entity-specific `Delete` methods (`ArticleService.DeleteAsync`, `StorageService.DeletePropertyAsync`) needed **no code changes at all**; the interceptor catches their existing plain `Remove()` calls automatically. `MyCollectables.razor`'s `DeleteCollectable` had its own manual per-image `ImageService.DeleteImageAsync` loop removed, now relying on the interceptor too - one implementation instead of duplicated logic that could drift.
  - **How state crosses the two-phase hook**: `SavingChangesAsync` (before the row - and its cascade-deleted `ImageAttachment` rows - are actually removed) walks `ChangeTracker.Entries()`, and for each `Deleted` `ISupportImageAttachments` entity, explicitly loads its `Images` navigation (`entry.Collection("Images").LoadAsync()`) if not already populated, since e.g. `ArticleService.DeleteAsync`'s `FindAsync(id)` doesn't `.Include()` it - the rows would otherwise be gone from the DB by the time cleanup could look them up. The captured list is then deleted for real in `SavedChangesAsync` (after the DB delete has committed) via the ALREADY-injected `IImageService.DeleteImageAsync`. State is passed between the two hooks via a `ConditionalWeakTable<DbContext, List<ImageAttachment>>` keyed on the specific `DbContext` instance, **not an interceptor instance field** - the interceptor itself is a singleton shared by every short-lived `DbContext` the app's `IDbContextFactory` creates, so an instance field would let concurrent `SaveChanges` calls from different circuits corrupt each other's pending-delete list (the exact class of bug this project's earlier `IDbContextFactory` conversion work was all about avoiding). `SaveChangesFailedAsync` clears the table entry on a failed save, for hygiene.

- **`ImageCleanupSaveChangesInterceptor` generalized into a reusable `EntityLogicUnit<T>` extension pattern (2026-09-12)**: prompted by the user noticing the single-purpose interceptor above and asking for a general-purpose way to plug save-time logic into `SaveChanges` for any entity type, not just image cleanup. New top-level `Interceptors/` folder (sibling to `Services/`/`Data/`/`Components/`) - `Services/ImageCleanupSaveChangesInterceptor.cs` is deleted entirely, its behavior migrated and this entry supersedes the one directly above.
  - **`Interceptors/EntityLogicUnit.cs`**: a new `EntityChangeType` enum (`Added`/`Modified`/`Deleted`, mapped from `EntityState`; `Unchanged`/`Detached` entries are skipped and dispatched to nothing), a non-generic `EntityLogicUnit` base (holds `CurrentContext` - the live, mid-save `DbContext`, exposed so a unit can do its own explicit-load of a navigation property it needs, e.g. `CurrentContext.Entry(entity).Collection("Images")` - and `LogError`/`LogErrors` protected helpers), and the generic `EntityLogicUnit<T>` implementations actually derive from (`T` is often an interface like `ISupportImageAttachments`, not just a concrete entity - the whole point is one unit can apply to every entity implementing it). Adding a new logic unit for a new entity type requires **zero `Program.cs` changes** - it's picked up automatically via reflection.
  - **Design point: async methods can't have `out`/`ref` parameters (a hard C# restriction, not a style choice)**, which ruled out the original "OnSaving(entity, out errors)" idea floated during design. Settled on a **shared, plain (non-`out`) `List<string>` passed into each logic unit's constructor** instead - mutating it via `.Add()`/`.AddRange()` propagates back to the caller just fine (only *reassigning* the parameter wouldn't, which is why `EntityLogicUnit` wraps it in `protected void LogError(...)`/`LogErrors(...)` rather than exposing the list directly, so a unit can't accidentally do that). This also cleanly solves multiple logic units for the same type needing to report into one combined error list - the interceptor creates one list per save and passes the same instance into every unit it constructs for that save.
  - **Design point: EF Core's free `OriginalValues` change-tracking snapshot is unreliable for this app's dominant delete pattern** - considered (and initially attractive, as a "free" way to let a unit inspect an entity's pre-change state) for a proposed capability to pass the original, pre-save version of an entity into `OnSaving`. But this app's established convention (short-lived `IDbContextFactory`-created contexts, with entities loaded in one context then re-attached via `.Remove()`/`.Update()` into a fresh context just to save) means EF has no continuous tracking history for most deletes/updates, so the free snapshot would silently just report current values as "original." Fixed by making original-fetching a **real, lazy, opt-in DB query** instead: `EntityLogicUnit<T>.GetOriginalFromDatabaseAsync()` does `context.FindAsync<T>(keyValues)` against a **fresh** `IDbContextFactory`-created context (not the live mid-save one) - correct regardless of attachment history, at the cost of a real round trip only paid by a unit that actually calls it. This "lazy opt-in" shape was chosen over an eager-fetch alternative that was also on the table.
  - **`Interceptors/EntityLogicUnitInterceptor.cs`**: the renamed, now fully generic `SaveChangesInterceptor` - it has zero entity-specific knowledge. Discovers concrete (non-abstract) subclasses of `EntityLogicUnit<>` once via reflection over the assembly (`static readonly Lazy<List<Type>>`, never re-scanned per save). On `SavingChangesAsync`, for each tracked entry whose state maps to a meaningful `EntityChangeType`, for each discovered unit type whose `T` the entity is an instance of, constructs the unit via `ActivatorUtilities.CreateInstance(scope.ServiceProvider, unitType, errors, context, keyValues)` - this is the key mechanism letting a unit's constructor mix real DI dependencies (e.g. `ImageCleanupLogicUnit`'s `IImageService`) with the three explicit, non-DI runtime values every unit needs, resolved by parameter type. One `IServiceScope` is created per `SaveChanges` call (not per-unit) and kept alive across the Saving→Saved boundary via a `ConditionalWeakTable<DbContext, PendingSaveState>` - the same per-`DbContext`-instance-keyed pattern the original interceptor used, necessary because the interceptor itself is a singleton shared by every short-lived `DbContext` the app's factory creates, so an instance field would let concurrent saves from different circuits corrupt each other's pending state. The scope is disposed once `SavedChangesAsync` (or `SaveChangesFailedAsync`, on failure) finishes with it. Any accumulated errors are logged via `ILogger<EntityLogicUnitInterceptor>.LogWarning` - no persistence yet, tracked below ("Entity logic unit error logging").
  - **`Interceptors/ImageCleanupLogicUnit.cs`**: the original image-cleanup behavior, now expressed as `EntityLogicUnit<ISupportImageAttachments>` with the exact same explicit-load-if-not-already-loaded logic the original interceptor had - captures the image list in `OnSaving` (before the cascade delete removes the rows) and deletes the physical files in `OnSaved` (after the DB delete has committed), same two-phase reasoning as before, just expressed as override methods instead of interceptor-hook bodies.

## IRC Event Logging API

### Overview
REST API endpoint for logging IRC events from Python bots to the SQL Server database.

### Endpoint
```
POST /api/irc/events
```

### Authentication
The API uses a static API key passed in the `X-Api-Key` header. Valid keys are configured in `appsettings.json` under `IrcApi.ApiKeys`.

### Request Headers
| Header | Required | Description |
|--------|----------|-------------|
| `Content-Type` | Yes | Must be `application/json` |
| `X-Api-Key` | Yes | Valid API key from configuration |

### Request Body
```json
{
  "action": "MESSAGE",
  "network": "Libera.Chat",
  "channel": "#mychannel",
  "target": "targetuser",
  "message": "Hello, world!",
  "sender": "botuser",
  "user": "someuser",
  "timestamp": "2025-10-10T12:00:00Z"
}
```
Note: `timestamp` is optional. If omitted, it defaults to the current UTC time.

### Fields
| Field | Type | Required | Max Length | Description |
|-------|------|----------|------------|-------------|
| `action` | string | Yes | - | Event type (see valid actions below) |
| `network` | string | Yes | 100 | IRC network name |
| `timestamp` | DateTime | No | - | UTC timestamp of the event (defaults to current UTC time if not supplied) |
| `channel` | string | No | 200 | Channel where event occurred |
| `target` | string | No | 200 | Target of the action |
| `message` | string | No | 4000 | Message content |
| `sender` | string | No | 100 | User who triggered the event |
| `user` | string | No | 100 | Additional user context |

### Valid Actions
`JOIN`, `PART`, `MESSAGE`, `QUIT`, `KICK`, `MODE`, `ACTION`, `NOTICE`, `CONNECT`, `TOPIC`

### Response
- **201 Created**: Event logged successfully, returns `{ "id": <int> }`
- **400 Bad Request**: Invalid action value
- **401 Unauthorized**: Missing or invalid API key

### Sample curl Call
```bash
curl -X POST https://localhost:5001/api/irc/events \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: your-api-key-here" \
  -d '{
    "action": "MESSAGE",
    "network": "Libera.Chat",
    "channel": "#mychannel",
```
